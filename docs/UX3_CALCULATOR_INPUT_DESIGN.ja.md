# 金額入力における電卓機能（式入力）設計メモ (PR UX-3 候補)

作成日: **2026-10-09**  
対象機能: 金額入力フィールドでの四則演算・数式評価 (`500+300`, `1000*2` 等)  
位置づけ: PR UX-2（金額・日付の柔軟な正規化）からの分離、次回PR UX-3での独立実装に向けた設計整理

---

## 1. 背景と目的

日常の家計記帳において、レシート合算（例: `320+150+98`）や複数個の購入（例: `250*3`）、割り勘・折半（例: `2400/2`）など、簡単な計算を行った結果を直接金額フィールドに入力したい場面が頻繁に生じる。

PR UX-2 では基盤整備として以下を実現した：
- 全角・半角数字の統一
- 正しい3桁カンマ区切りの許容
- 通貨の最小単位（quanta）への厳密な整数変換
- 不正入力時のドラフト保持

本メモ（UX-3候補）では、Coreの会計不変条件と「浮動小数点数・暗黙の推測を一切排除する」方針を完全に守りつつ、金額入力欄で算術式を安全・確実に評価するための仕様と設計を定義する。

---

## 2. コア原則と会計上の不変条件

Bakhloの基本方針に従い、以下の制約を厳格に課す。

1. **浮動小数点数（IEEE 754 `float`）の絶対排除**
   - 金額の計算に `float` は一切用いない。
   - `0.1 + 0.2` による微小誤差や表現不能値の混入を原理的に防ぐ。
2. **正確な整数・有理数（Exact Rational / Integer Quanta）演算**
   - 内部計算は `Zarith` (`Z.t` および必要に応じて `Q.t`) を用いた正確な有理数演算で行う。
3. **暗黙の丸め（Round / Truncate）の禁止**
   - 除算（`/`）において、通貨の小数桁数（scale）で割り切れない場合（余りが生じる場合）、暗黙の四捨五入や切り捨てを行わない。
   - 割り切れない場合は即座に検証エラー（例: `割り切れない金額です` / `indivisible-amount`）を返し、推測による誤差混入を拒否する。
4. **ゼロ除算の厳格な拒否**
   - ゼロ除算（`/ 0`）は例外でクラッシュさせず、入力エラー（例: `ゼロで除算することはできません` / `division-by-zero`）として安全に捕捉する。
5. **正の金額（Positive Amount）の要求**
   - Coreの取引意味論に従い、計算結果は厳密に正（`> 0`）でなければならない。
   - 計算結果が `0` の場合は `ゼロの金額は記帳できません`、負値の場合は `負の金額は記帳できません` として拒否する。
6. **境界での正規化とドラフト保持**
   - 式の評価はUI/入力境界で行い、Coreの数量型・永続化フォーマットには最終的な `Z.t` quanta のみを渡す。
   - 式の構文エラーや計算エラーの際、ユーザーが入力した数式文字列をそのままフォームに保持する。

## 3. 文法および仕様

### 3.1 許可する記号と正規化

UX-2で整備した文字正規化ルールと統一する。

| 種類 | 半角（内部表現） | 許容する全角文字 | 備考 |
| :--- | :---: | :---: | :--- |
| 数字 | `0` - `9` | `０` - `９` | 半角へ正規化 |
| 小数点 | `.` | `．` | 通貨の小数桁まで |
| 桁区切り | `,` | `，` | 正しい3桁区切りのみ（計算前に検証・除去） |
| 加算 | `+` | `＋` | 二項演算 |
| 減算 | `-` | `－` | 二項演算 |
| 乗算 | `*` | `＊`, `×` | 二項演算 |
| 除算 | `/` | `／`, `÷` | 二項演算（厳格な整除） |
| 括弧 | `(`, `)` | `（`, `）` | 優先順位指定（将来拡張または初期サポート） |
| 空白 | ` ` | 全角空白 | トークン間の空白は無視 |

### 3.2 演算子の優先順位と結合規則

- 優先順位: 括弧 `()` > 乗除算 `*`, `/` > 加減算 `+`, `-`
- 結合規則: 左結合（`10 - 3 - 2` = `(10 - 3) - 2` = `5`）
- 単項演算子: 先頭や演算子直後の `-`（負数）は、減算結果が最終的に正になる場合であっても構文の曖昧性を避けるため、第一段階では二項演算のみに絞るか、括弧内でのみ検討する。

### 3.3 計算例と合否基準

通貨: JPY (scale = 0) の場合：
- `500 + 300` → `800` (受理)
- `1,000 * 2` → `2000` (受理)
- `１０００＋５００` → `1500` (受理)
- `1000 - 300` → `700` (受理)
- `1000 - 1200` → 負値エラー (拒否)
- `2500 / 3` → 余りが出るため割り切れないエラー (拒否)
- `2500 / 2` → `1250` (受理)
- `500 / 0` → ゼロ除算エラー (拒否)
- `500 +` → 構文エラー (拒否)

通貨: USD (scale = 2) の場合：
- `12.50 + 3.75` → `16.25` (受理)
- `10 / 4` → `2.50` (scale 2で割り切れるため受理)
- `10 / 3` → `3.3333...` (scale 2で割り切れないため拒否)

## 4. アーキテクチャと責務配置

```
[ TUI (Notty / Bonsai) ]
       │ 入力文字列 (raw string, 例: "500 + 300")
       ▼
[ application / sexp: parse_amount / evaluate_expression ]
       │ 1. 文字正規化（全角→半角、カンマ検査）
       │ 2. 字句解析・構文解析（AST生成）
       │ 3. Exact Rational評価（Q.t / Z.t）
       │ 4. scale適合性・正値検査
       ▼
[ Core: Quantity.t / Transaction ] (不変: 単一の確定quantaとして受領)
```

1. **純粋モジュールでの実装**:
   - `sexp/daily_book.ml`（または `application/amount_calculator.ml`）に独立したパーサ・評価器を実装する。
   - `Q.t`（有理数）を用いて中間計算を行い、最終的に `target_scale` の整数倍（整数quanta）になるか検査する：
     $$Q = \frac{\text{分子}}{\text{分母}}$$
     $$\text{Quanta} = Q \times 10^{\text{scale}}$$
     $\text{Quanta}$ の分母が $1$ であれば割り切れており、整数の分子を `Z.t` として採用。分母が $1$ でなければ丸めずに拒否。
2. **デュアルTUIの共通利用**:
   - Notty・Bonsai_term のどちらも共通の関数を呼ぶだけであり、UI層には計算ロジックを持たせない。
3. **下書き保持**:
   - 評価エラー時は `Invalid_amount (raw_text, reason)` などのエラー型を通じて、ユーザーの入力した式をそのまま `form.amount` に維持する。
