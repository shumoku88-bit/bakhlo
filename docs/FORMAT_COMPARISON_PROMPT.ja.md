# OCaml製家計アプリの正データ形式：S式と独自fact textの比較

以下の条件で、二つの形式を独立に評価してください。S式が有利とも、依存ゼロが有利とも決めつけず、長期的な総コストと所有者の扱いやすさで判断したいです。

これは設計相談です。すべての例は架空で、実データ・個人情報・実際の利用状況は含みません。例の構文は未採用・未実装で、完全な世帯データのスキーマでもありません。

## 1. 背景

- Bakhloという独立したOCaml製の「家計に関する小さな質問に答えるアプリ」を開発しています。AIなしでも動くことが前提です。
- 家計の正データは既存のLOAMが保持しています。より良い設計なら移行は選択肢ですが、まだ移行先も移行処理も採用していません。
- 所有者が専用アプリなしでもデータを読め、必要なときに管理できるテキストを重視します。編集内容は検証・公開手続きを通す提案であり、稼働中の原本を直接書き換える運用ではありません。
- 既存のファイル配置や構文を永久に維持する必要はありません。ただし意味・履歴・根拠・識別子を失ったり、推測で埋めたりする移行は不可です。
- 今はUnix上で検証しています。将来MirageOSも目標ですが、直ちにその実装を求めるものではありません。
- 構文、論理スキーマ、ファイル分割、公開の原子性、バックアップ、実行環境は別の決定です。今回の主題は構文とその実装・保守コストです。

## 2. 両案に共通の意味と制約

両案は同じ「事実・観測・明示的な関係・方針」を保存します。S式にするか独自構文にするかで、保存内容を変えてはいけません。

1. 数量は符号付きの無限精度整数quantaです。OCamlの機械整数やfloatへの変換、丸めは不可。単位に相当するMeasureと所在Locusは別の識別子です。表示尺度も解釈に影響します。
2. EventのEffectは個々の出現とキーを保持します。同じ座標だからといって集約して消してはいけません。例は単一Measureの均衡移動ですが、すべてのEventがこの種類とは限りません。
3. 訂正は元のEventを残し、明示的な参照で結びます。日付の改訂、Reversal、履行関係はEvent訂正とは別です。現在の状態は関係から求め、行順や日付で「最後が正」と推測しません。記録時刻を過去に遡って作りません。
4. 残高の観測は活動履歴から導いたキャッシュではなく、独立した情報です。観測に結びついた「どのEventの根が反映済みか」という集合（reflected-root cut）も保持します。cutを日時やファイル位置から推測しません。観測グループには安定した家計上のIDを強制しません。
5. 不明、未供給、明示的な空、既知のゼロ、非ゼロだが数量不明を混同しません。欠落した項目に空や0を自動補完しません。識別子のtrim・大文字小文字変換・Unicode正規化も勝手には行いません。
6. 過去に使われた所在と、新規記録を許可する所在は別です。分類・振り分け・新規記録の許可は独立した明示的な方針です。
7. 論理リクエストから、そのリクエストが作った元のEventへの対応は公開の来歴です。後の訂正先に付け替えません。この対応だけで保存成功や支払いの同一性を証明したことにはなりません。
8. 現行の仕訳出力は一部の履歴・観測根拠・方針を省く表示です。それだけで正データを代替できません。ただし、hledger等のあらゆる拡張形式が表現不能だと主張しているわけではありません。
9. 未対応・未知の情報は勝手に削除せず、保持し、未検証であることを明確にします。保持しただけで意味を検証済みにせず、不適切な回答や書込みは拒否します。

全体には実績、予定、配分、注意・期限、履行・決済、分類・振り分け、許可、開始量・観測・履歴の完全性に関する根拠などがあります。下の例はそのごく一部です。現在のUIが使わない情報を不要とは見なしません。

## 3. 案A：S式 + 最小限の既存パーサ

- S式の構文解析にはJane Street系の`parsexp`を使い、`sexplib0.Sexp.t`のAtom/Listを、明示的な保存スキーマに沿って検証します。
- 内部のOCaml型の`[@@deriving sexp]`出力を、そのまま永久的な保存形式とはしません。
- 構文が読めても、重複・欠落項目、未対応バージョン、識別子・参照・数量・全体整合性は別途検証します。

```lisp
(bakhlo
  (version 1)
  (measure (id "jpy") (scale 0))
  (event
    (id "E1")
    (occurrence-day "2000-01-01")
    (description (text "架空例"))
    (effects
      (effect (key "k1") (locus "wallet") (measure "jpy") (quanta -10))
      (effect (key "k2") (locus "food")   (measure "jpy") (quanta 10))))
  (event
    (id "E2")
    (occurrence-day "2000-01-01")
    (description (absent))
    (corrects-event "E1")
    (effects
      (effect (key "k3") (locus "wallet") (measure "jpy") (quanta -15))
      (effect (key "k4") (locus "food")   (measure "jpy") (quanta 15))))
  (observation-group
    (reflected-roots "E1")
    (assertions
      (assertion (locus "wallet") (measure "jpy") (quanta 1000))))
  (request-origin (request-token "req-1") (original-event "E1")))
```

## 4. 案B：独自fact text + 自前の小さな読み書き器

- 名前付きの項目と行・ブロックを使う、所有者向けの独自テキストです。`{}`はこの候補の仮表記であって、採用済みの文法ではありません。例は比較のために項目構成を揃えたもので、既存の実験的読み取り器がこの文法を実装済みだという意味ではありません。
- 追加の構文解析ライブラリなしで実装する案です。ただし、引用・エスケープ・コメント・字句境界・エラー位置・整形など、自分たちで管理する範囲が生まれます。
- 案Aと同じ保存スキーマ、同じ意味の検証を行います。依存がないから安全・単純だと最初から仮定しません。

```text
bakhlo 1
measure "jpy" { scale 0 }

event "E1" {
  occurrence-day "2000-01-01"
  description text "架空例"
  effects {
    effect key "k1" locus "wallet" measure "jpy" quanta -10
    effect key "k2" locus "food"   measure "jpy" quanta 10
  }
}
event "E2" {
  occurrence-day "2000-01-01"
  description absent
  corrects-event "E1"
  effects {
    effect key "k3" locus "wallet" measure "jpy" quanta -15
    effect key "k4" locus "food"   measure "jpy" quanta 15
  }
}
observation-group {
  reflected-roots ["E1"]
  assertions {
    assertion locus "wallet" measure "jpy" quanta 1000
  }
}
request-origin request-token "req-1" original-event "E1"
```

両方ともE1を残し、E2から訂正関係を明示し、観測とcutを結び、リクエストの対応をE1に保持しています。保存レイアウト・履歴リプレイ・計算済み残高を指定する例ではありません。

## 5. 依存について確認済みの事実

現在のOCamlは5.3.0で、Base、Zarith、`sexplib0 v0.17.0`、`ppx_sexp_conv v0.17.1`は導入済みです。`parsexp`とフルの`sexplib`は未導入です。

公開opamメタデータでは、`parsexp v0.17.0`は以下を要求します。

- OCaml >= 5.1.0
- sexplib0 >= v0.17 かつ < v0.18
- Dune >= 3.11.0

現在の構成では案Aの追加候補を`parsexp`一つに抑えられます。フルの`sexplib v0.17.0`はこれらに加えて`num`も要求するので、案Aはそれを前提にしていません。

ただし依存メタデータの確認だけで、実装の正しさ、ライセンス適合性、性能、メモリ、バイナリサイズ、MirageOS適合性を実証したことにはなりません。追加パッケージ数だけで総コストを判断しないでください。

## 6. 検討してほしいこと

1. 両案に共通するスキーマ・意味検証の負担と、構文によって変わる負担を分けて比較してください。例の表記だけで案Bが短い、案Aが堅いと決めつけないでください。
2. 読みやすさ、手編集時の間違い、引用・日本語・改行、重複/欠落項目、エラー位置、整形、Git差分、長期的な形式変更を比較してください。必要なメモは保存項目として保持し、非意味コメントとは区別します。AST再出力によるコメント・書式の消失も検討してください。
3. 開発・テスト・長期保守、自作パーサの責任、外部依存の更新制約、サプライチェーン、移植性、入力サイズ・深さ・メモリの制限を評価してください。未測定の速度・サイズ・移行費用を数値で捏造しないでください。
4. スキーマが今後増えても、独自構文を小さく保てるか。逆にS式の自由度が過剰な構文や複雑な検証を招くか。Bakhloの範囲で具体的に説明してください。
5. 構文解析成功と意味の検証、意味の検証と安全な公開、表現変換と履歴/識別子の変更を混同しないでください。S式でも独自構文でも、原子的公開・復旧・移行の安全性が自動で得られるとは見なさないでください。

出力は次の順でお願いします。

- 第一候補とその理由。反対案を選ぶべき条件も示す。
- 比較表。事実・推測・未測定を区別する。
- 例の問題点と、同じ意味を保った最小限の改善案。
- 決定に必要な未解決事項と、少数の合成データ例でできる限定的な比較。巨大な新テスト基盤や両形式のフル実装を最初から要求しない。

必要なら第三案を一つだけ提示できますが、明確な改善理由がある場合に限ってください。実データの提供や今すぐの移行・依存追加は求めず、この材料だけで判断できる範囲と限界を明記してください。
