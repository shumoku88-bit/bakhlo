# Bakhlo保存方針：年別S式を第一実装にする

> **廃止（2026-10-20）**: 年別S式・`Year_read`・Recordsはユーザー判断で削除した。この文書は経緯の記録で、現在の方針はAGENTS.mdの Storage direction と[長期保存調査の第5段階](../LONG_TERM_STORAGE_STUDY.ja.md)。

2026-10-17 決定。実装の追跡: [#34](https://github.com/shumoku88-bit/bakhlo/issues/34)。

## 結論

**暦年（1月1日〜12月31日）ごとに独立したS式テキスト帳簿を持つことを、Bakhloの最初の長期運用向け保存方式の実装方針とする。**
現在の単一S式の入場・書込・復旧部品を使う。これは、年度別の本番用保存方式が**実装・運用認定済み**という意味ではない。

Irminは[合成Git保存実験 PR #32](https://github.com/shumoku88-bit/bakhlo/pull/32)と[Core接続候補 PR #33](https://github.com/shumoku88-bit/bakhlo/pull/33)、[Phase 2実験](IRMIN_PHASE2_RESULTS.ja.md)で得た知見を残し、将来の**交換候補**にする。本体の依存には追加しない。Tackler/Git案 [PR #30](https://github.com/shumoku88-bit/bakhlo/pull/30)は任意の参考資料であり、年ごとのGitブランチも必須にしない。

S式は**論理データの表現**、年別ファイルやIrminは**物理保存**。一方を選ぶことはもう一方の形式を排除しない。ただし今は汎用プラグインや、正データの二重管理・自動バックエンド切替は作らない。将来Irminへ移す場合は、明示した独立バックアップ、変換、Coreでの再入場・意味同等性、単一の権威への切替と復旧を別途検証する。

## 使う人から見た到達目標

通常の帳簿は `books/2026.sexp`、次の年は `books/2027.sexp` のように**明示的に選択**する。これは例示パスであり、現行TUIの自動年度切替機能を意味しない。

- 当年の記帳と通常の訂正は**その年のファイル**を保存する。他の年度ファイルを書き直さない。
- 2026-12-31と2027-01-01の境界を厳密に検査する。日付変更で年度が移る場合は、複数ファイルへの安全な移動が実装されるまで**拒否**する。IDは変えない。
- 年末から翌年への繰越は**元が検証できる派生情報**とし、独立した残高観測に置き換えない。Exact／明示ゼロ／存在のみ／不明、反映済rootとOpeningSupport、未完了予定、必要な固定元参照を消さない。繰越未実装の間は**翌年の残高を引き継いだかのように表示しない**。
- 年をまたぐ予定の支払い、過年度訂正、別年度へ移る明細、複数年度の比較は、年別ファイルへ機械的に分割しただけでは動かない。必要な参照閉包と**同一の整合した選択状態**を検証するまで、該当操作を拒否する。
- 年金の隔月サイクル・任意の分析期間は暦年と独立。日付・支給日を年境界から推測しない。

## 最初の実装は1つの縦切りだけ

[#34](https://github.com/shumoku88-bit/bakhlo/issues/34)の先頭チェックリストに従う。

**最初の合格条件**: 合成2026年ファイルを明示選択して、普通の記帳→訂正→終了→再起動ができる。2027年の新規ファイルを利用者の確認で作り、同じ操作ができる。2026年の全バイト列を勝手に変えず、年度違いの新規記帳・日付訂正は拒否。読込不正・不確かな書込結果は黙って修復／再試行しない。

年越し時に正しい繰越込み残高を出す実装は**次の別slice**。無理に最初のsliceへ盛り込まない。既存`Daily_book`、`tui/daily_file`、`Year_read`を再利用し、第二の会計エンジンや保存機構は作らない。ファイル1本の安全な保存と、複数ファイルを同時変更する場合の原子性は別問題であり、後者は未認定。
