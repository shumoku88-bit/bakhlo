# LOAM → Bakhlo：機能棚卸しと乗り換え判定表

**方針：まず記帳＋支払い予定、各種残高、LOAM Home `d` のDaily Paceと必要なレポートで
実運用のやりくりを試す。budgetは切替条件から外して保留し、これらで足りれば採用しない選択もある。
Attentionの以前の要望は維持。TUIは機能フォーカス＋フローティングペイン。
安全な切替条件と詳細は検討中。実装・切替の完了表でも、即時の正データ切替許可でもない。**

## この一覧の役割

「LOAM全部を実装する」でも「少し動いたので乗り換える」でもなく、
**どの生活操作ができれば普段の記帳先をBakhloに替えるか**を、人間とpitが同じ表で決める。
必要な表現力は保ち、LOAMの研究機構・ファイル構成・画面配置まで再現する義務にはしない。

ユーザーが選んだ中心と、実運用を見てから判断する機能を分ける。

| 分野と扱い | 生活上の回答・操作の最小案 | 詳細を決める対象 |
| --- | --- | --- |
| 予定関連：中心 | 作成・変更・取消・支払い、未払いの確認 | S01–S06：定期補充・未補充確認の範囲。S07はbudget採用時のみ |
| 各種残高：中心 | 口座×通貨の残高、必要な種類の残額を確認 | B01–B08、V03、F04–F06：過去残高・純資産・精算残額の要否。予算残額とは別 |
| 今日いくら使えるか：中心 | LOAM Home `d` のDaily Pace（残高プール型） | V11：計算の種類は決定。対象口座・期間設定の持ち越し、表示と推移の範囲 |
| 必要なレポート：実際の問いから選ぶ | 記帳・予定・残高からやりくりに必要な集計を読む | V01–V08等：項目・期間・根拠を個別に選び、budgetを前提にしない |
| 予算周り：保留・任意 | 配分なしで実運用を試し、不足した場合に要否を判断 | S07、P01–P03、V09は初回切替の必須条件ではない |
| Attention：以前の要望を維持 | 気になる確認事項・期限を残し、解決／取り下げる | V10：必要な一覧・入力・持ち越し範囲 |

**budgetなしで成立するかを見ることが今回の方針。LOAMの機能数に合わせて足さない。**
既存の予算API・v4保存契約・保持済み情報は維持する。不要機能の判断とコード／データ削除は別。
予定と実績を併せて見る場合も、未払い予定を実残高へ足したり、支払い済み分を二重控除しない。
先に挙がった複数ポスティング入力（R02）も重点のまま維持する。
未決定をpitが勝手に「不要」または「全部必須」に変えない。
製品に必要な分野と、**最初の切替日に必要な操作・条件**を分けて決める。

## 調査範囲と読み方

- LOAM：`f82f4c45498ce9b3c51a76acb7189588a5f74718` の文書、実行入口、操作・表示・発行境界を読んだ。
- Bakhlo：初版は `e1e010818ef02d1b3ea6b38d4ea276cdb8c26532` と当時のDaily_book／TUI接続。
  準備では `0d9ae2f` の `daily_book.mli`、数量問い合わせ、TUI対応範囲を再確認した。
  現行コードは予定更新API、`daily_pace`現在値照会、Daily v4の明示的な期間予算APIを追加した。
  合成テストで現在値の構成を確認済み。LOAM実行結果との一致・移行の認定ではない。
  以下の「日常経路」はAPIだけの対応を画面から操作済みとは数えない。
- 今日の目安はLOAMの `CycleSpendingPaceReview`、Home `d` の分岐、`DailyPaceTrend` を確認。
  `d` はDaily Paceの推移を開き、現在の点も同じ残高プール型の計算に基づく。
  以下の計算・受入案は設計準備であり、Bakhloでの実装済み・実行一致の主張ではない。
- **実データ・私的設定は調べていない。LOAMのビルド・起動・移行もしていない。**
  したがって「この家庭で使っているか」はユーザーが決める。機能の存在と使用実態を混同しない。
- 古い調査文書の「未実装」より、現在の実行入口と操作元を優先した。
  たとえば現在のReportsにはIncome & Expense、役割別Balances、Multicurrency Spendがある。
- 主たる比較対象は **`tools/tui`（Bonsai_term）と `bakhlo-daily`**。
  旧Book用の `record`／`exchange` CLIが持つ能力は、別形式のままなのでDaily TUIの対応済みに数えない。

Bakhlo欄の意味：

| 表記 | 意味 |
| --- | --- |
| 試用可 | 新しい日常TUIから操作できる。実運用への切替・耐久保存の認定ではない |
| 一部 | 使える範囲と不足を同じ欄に明記した |
| データ／検査のみ | 保存形式や検査はあるが、普通の画面操作につながっていない |
| 未接続 | LOAMの該当機能に相当する日常操作・回答が新しい台帳経路にない |
| 未調査 | 存在・接続を確認できていない。未実装と断定しない |

切替欄は実装の完了印ではなく、**範囲を選ぶ判断**。
「必須分野」はユーザーが必要とした分野。行内の詳細全部が確定した印ではない。
「重点」は先に挙がった検討対象。「必須候補」はpitの提案、
「要判断」は未決定、「後で候補」は初回切替から外せそうな提案。
いずれも判断を変更できる。
根拠の `[L1]` 等は末尾の読み取り専用参照。

### 記帳UIの認知負荷も切替条件に含める

記帳の切替判定では、Coreが表現できることだけでなく、**人間が既存の口座・費目を覚えていなくても、
確認・検索・選択して安全に記帳できること**を評価する。これは新しい家計意味論ではなくUI補助だが、
日常の正データを任せるための実用要件である。

BakhloのHomeは、すべての情報を常時並べるダッシュボードにしない。Bonsai_termを使う
日常UIは、上に記帳下書き、下の広い領域に選択した一種類の閲覧内容を置く。
Tabで領域を切替え、矢印は領域内に限定する。操作helpと残高contextはfocusに合わせ、
必要な選択・詳細・確認は短命なpaneに出す。現行の下は明細／予定のみ。
**下書きの取引全体は見えるまま、非選択の一覧や不要なhelpは出し続けない。**

候補選択、検索、新規Locus追加、明細詳細、記帳previewなどは、Homeへ常設列を増やす代わりに
必要な間だけ開くfloating／overlay paneを使える。具体的なwidget APIや画面配置は実装時に選び、
pane（将来のWeb UIを含む）ごとに別の家計意味論を持たないことを優先する。focusやpaneの開閉はpresentation stateであり、
canonical data、Locus admission、残高根拠、publication authorityにはしない。

受入の最低例は、既存Locusの名前を思い出せない状態から一覧／検索で正しい候補を選び、
複数postingを完成し、全体previewを確認して保存できること。新規Locus追加では既存候補を先に確認でき、
似た名前を人間の記憶だけで重複作成しなくて済むこと。

予定が記録されていない日は「支払い義務なし」と断定しない。
周期だけから事実としての予定を勝手に作らない。

### 今日の目安と「各種残高」を混ぜない

**決定：今日の額はLOAM Home `d` のDaily Paceを採用する。**

```text
（明示した同一通貨の口座プールの既知残高
 − 期間末より前の未払い予定による純流出）÷ 残日数
```

期限超過の未払いも控除する。プール内振替は差引ゼロ、予定収入は実績化前に加えない。
残日数は観測日から明示的な期間末（排他的）まで。LOAM Homeはローカルの今日を観測日に使い、
カレンダーで移動した日付を使わない。最小単位の整数除算を含め、LOAMの計算を基準にする [L13]。
未知残高・不正な期間・残日数0は計算不可とし、赤字をゼロへ丸めない。

用途別の「配分 − 実績 − 管理対象予定」を日割りするCycle Budgetの表示 [L7] は別物。
今日の額の実装条件に加えず、予算機能の範囲で必要なら扱う。

表示は今日の目安を簡潔に、元の残高・控除した予定・残額・残日数・対象通貨と未確認事項は
同じ機能の詳細ペインで確認できるようにする。支出の安全性や予定の網羅性を保証する数字ではない。
物理残高・資産／負債・精算残額・予算残額は、それぞれの明示的な根拠から答える。
Attentionの存在や解決は残高・予定の支払いを変更しない。

残る設定・表示の確認：対象口座・期間設定の持ち越し、通貨スケールに沿う表示、
未確認事項の見せ方、`d`にある直近7日の推移も初回に表示するか。
推移は現在の記録から再構成した値であり、当時表示した額のログではない。
名前から口座を選ばず、月初／月末を既定にしない。日割り額そのものは保存しない。
現在残高の根拠だけで過去の日割り履歴まで保証しない。

## 機能とは別に、データの持ち越しを決める

**新しい台帳が読めることは、全家庭データが移ったことではない。**
現在の候補作成は限定された読み取り・変換であり、完全バックアップでも全面移行でもない。
ここでは私的なファイルの内容や使用状況を判定していない。

| 情報の種類 | 現在の候補／Dailyで扱う範囲 | 切替までに決めること |
| --- | --- | --- |
| 実績・日付・摘要・postings・識別子 | 訂正済み状態へまとめ、元入力版は別に保全 | IDと必要な参照を守り、正確な量・通貨を保つ。新しい正データに永久の訂正鎖は不要 |

画面を後回しにすることと、その情報を捨てることは違う。

普段の実績記帳を二重化したり、自動同期して解決したことにはしない。

## 切替範囲を確定する手順

1. **この表をユーザーと仕分ける**：「切替前に必須／切替後でよい／使わない」を選ぶ。
   最初は下の質問で必要分野の詳細を決め、該当IDへ反映すればよい。全行を一度に判断する義務はない。
   手作業や外部道具で当面代替するものには、その方法を短く添える。未決定は未決定のまま残す。
2. **合意した必須の生活操作を実装する**：下の小さな段階案から一つずつ選ぶ。
   記帳UIではR09〜R13も同時に仕分け、Core能力だけでなく人間が迷わず選択・確認できるかを切替条件にする。
   不足の共通処理だけ足し、任意の棚卸し行をpitの自動実装キューへ入れない。
3. **必須分だけで一周試す**：合成データで複数行の記帳・再開・訂正、予定の作成・変更・取消・支払い、
   口座×通貨の残高確認を行う。Daily Pace・必要なレポート・Attentionの選んだ範囲も確認する。
   budgetはこの一周の前提にしない。
   使う外貨・精算があればその操作を加える。
4. **データと運用を確認する**：必要な情報・設定の持ち越し範囲、元データの保全、読戻し、
   バックアップからの復元、失敗時の確認方法を決めて試す。選んだ答えについて独立した期待値で照合する。
   永久ログ、LOAMと同じ保存機構、全研究ツールの再実行は条件にしない。
5. **ユーザーが切替を明示的に決める**：それまではLOAMが正。切替日・記帳先・保全元を確認し、
   pitが「実装できたから移行済み」と判定しない。

### TUI：機能フォーカスとフローティングペイン

**ユーザー指定：常用の記帳と閲覧を上下2領域に分け、補助操作だけフローティングにする。**
記帳の取引全体は上に保ち、下には選択した種類の内容だけを表示する。
非選択の残高・予定・予算・Attentionを全部並べることも、入力中の一項目以外を隠すこともしない。

- **上：記帳**：新規は出金元から。↑↓で項目移動し、端でも下へ落ちない。
  ←→は通貨・科目の候補、文字欄では文字位置。科目Enterはpicker、それ以外は全体preview。
- **下：閲覧**：←→で種類、↑↓で一覧選択、Enterで詳細。現在は明細／予定のみ接続。
  予定詳細からの支払い入力は上（複数行なら入力pane）へ戻す。記録なしを義務なしとしない。
- **Tab／Shift-Tab**：上下領域を切替え、元の入力項目・文字位置／一覧別の選択位置を保持。
  領域見出しを反転・`>`で示し、helpと残高contextは入力先に合わせる。
- **フローティングペイン**：picker、明細／予定詳細、複数行入力、取引確認等の補助操作。
  背面キーを遮断し、閉じると元のfocusへ戻る。自由配置・多重ウィンドウ管理は作らない。
- **下書きと安全性**：閲覧切替だけでは上の下書き・モード・保持した複数行を変えない。
  別明細の編集／支払いが金額・メモ・編集／支払いモード・複数行を置換する場合は拒否し、
  Ctrl-Nでの明示的な破棄と保存を分ける。競合・結果不明の警告と書込み停止は隠さない。
  狭い端末では拡大案内を表示し、確認paneは32桁×10行未満の確定を拒否する。

現行の上下focus・明細／予定切替・詳細からの支払い入力は両frontend共通で接続済み。
残高・Daily Pace・予算等の追加表示と科目追加paneは未接続で、空の入口を先に増やさない。
表示のために台帳形式・保存API・依存を増やさない。

共有回帰と両renderer self-checkは領域境界・選択復帰・文字位置／貼付・保持した複数行・
予定詳細／置換拒否・支払いfocus、全テーマ・端末寸法・警告を確認する。合成Terminalテーマの
実PTYも両方向の再起動／編集・上下移動・文字位置・閲覧切替・複数行再開／支払い・端末復元を通過。
人間のUX受入や実運用切替の認定ではない。

### 肥大化を避ける境界

- 足す単位は「生活操作＋意味を持つ最小データ＋既存テスト＋画面からの接続」。
  空のモジュール、汎用スケジューラ、ワークフロー／残高フレームワーク、第二の保存経路を先に作らない。
- 計算は純粋、保存は既存の明示的I/O、画面は共通の結果を表示する。
  画面（TUIの各pane・将来のWeb UI）や旧Bookで同じ計算を別々に実装しない。
- 保存するのは必要な根拠と明示した設定。現在残高・予算残額・日割り目安・期限超過表示は導出する。
  正確な残高観測は独立情報であり、表示残高のキャッシュとは別。
- 形式拡張が必要な段階でだけバージョンと明示的変換を決める。旧形式を黙って再解釈せず、
  未対応フィールドを捨てて保存しない。永久の訂正鎖やLOAMの内部レイアウトは移植しない。
- 既存の `test/daily_book_tests.ml` 等へ受入例を足す。新依存・研究ツール群・生成物・
  実データfixture・並行移行コンバータは準備だけで増やさない。
- 棚卸しと段階案はこの文書、直近の作業はHANDOFFに集約する。分野ごとの計画書や作業日誌を増やさない。
  各段階で必要性のない試作・重複を残さず、履歴はGitに任せる。

**画面接続前の機能を先に実装する段階へ進んだ。単発予定の作成・変更・取消APIと
合成テスト、Daily Pace現在値、明示した期間予算の純粋API／保存は実装済み。
予算は記録上の対象科目集計と既知予定までで、資金裏付け・履歴・網羅性は未対応。Attention、残高等の追加画面は未実装。
未決定の詳細を既定値へ固定せず、実データの追加読取・変換・正データの切替は行わない。**
